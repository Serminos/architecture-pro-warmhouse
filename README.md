# Задание 1. Анализ и планирование
### 1. Описание функциональности монолитного приложения

**Управление датчиками (sensor):**

- Пользователь может создать запись о новом датчике, указав название, тип (в текущей реализации доступен только тип temperature), 
местоположение (например, "гостиная", "спальня" и т.п.) и единицы измерения. Данные сохраняются в таблице sensors базы данных PostgreSQL.
- Система позволяет получить список всех зарегистрированных датчиков или информацию о конкретном датчике по его идентификатору.
- Пользователь может изменять атрибуты датчика: название, тип, местоположение, единицы измерения, значение и статус (активен/неактивен).
- Есть возможность удаления записи о датчике по его ID.
- Через отдельный эндпоинт PATCH /sensors/{id}/value можно вручную установить текущее значение и статус датчика.

**Мониторинг температуры(temperature_service):**

- При запросе списка датчиков или конкретного датчика типа temperature система выполняет синхронный HTTP-запрос 
к внешнему сервису temperature-api, чтобы получить актуальное значение температуры. 
Полученные данные не сохраняются в базу данных, а только подставляются в ответ пользователю для отображения.
- Отдельный эндпоинт GET /sensors/temperature/:location позволяет получить текущую температуру для заданного 
помещения напрямую у внешнего API, без обращения к локальной БД.
- Датчики не передают показания самостоятельно. Система всегда инициирует запрос к внешнему API в момент обращения пользователя (pull-модель).

**Особенности текущей реализации**
- Согласно бизнес-описанию компании, пользователи должны иметь возможность удалённо включать и выключать систему 
отопления в своих домах на основе данных от датчиков температуры. Однако в предоставленном коде эта функциональность отсутствует. 
Приложение ограничивается только управлением датчиками и отображением температуры. 
Логика принятия решений об отоплении, команды на исполнительные устройства (реле, котёл) не реализованы.
- Все операции выполняются синхронно и последовательно.
- Отсутствует аутентификация и разграничение прав доступа - любой пользователь может управлять любыми датчиками (создавать, изменять, удалять).
- Данные, получаемые от внешнего API, не кэшируются и не сохраняются, что создаёт жёсткую зависимость от доступности сервиса temperature-api.
- Подключение физических датчиков к системе требует выезда специалиста. Самостоятельное подключение пользователем не поддерживается.

### 2. Анализ архитектуры монолитного приложения
- Язык программирования: Go
- Веб-фреймворк: Gin
- База данных: PostgreSQL с использованием пула соединений (pgx/v5/pgxpool)
- Тип архитектуры: монолит (все компоненты в одном процессе).
- Взаимодействие: синхронное (HTTP REST API, прямые SQL-запросы к БД, синхронные вызовы внешнего API).
- Модель данных: одна таблица sensors, её поля
- API endpoints:
  - POST /api/v1/sensors - создание нового датчика
  - GET /api/v1/sensors - получение списка всех датчиков
  - GET /api/v1/sensors/:id - получение конкретного датчика
  - PUT /api/v1/sensors/:id - полное обновление датчика
  - DELETE /api/v1/sensors/:id - удаление датчика
  - PATCH /api/v1/sensors/:id/value - ручное обновление значения и статуса датчика
  - GET /api/v1/sensors/temperature/:location - получение текущей температуры для указанной локации (обращение к внешнему API)
- Масштабируемость и развёртывание: ограничения (вертикальное масштабирование, необходимость остановки приложения при деплое, использование Docker).
- Проблемы текущей архитектуры: (смешение логики, отсутствие слоя репозитория, нет кэширования, нет аутентификации, данные из внешнего API не сохраняются).

### 3. Определение доменов и границы контекстов (целевая декомпозиция)
Домен управления пользователями (User & Access Management)
- регистрация и вход пользователей
- управление ролями (владелец, житель, гость) и правами доступа к конкретным домам/устройствам
- приглашение других пользователей в дом с назначением роли

Домен управление домами (Home Management)
- Создание дома, добавление/удаление комнат
- Настройка общих параметров дома (часовой пояс, геолокация и т.п.)

Домен управление устройствами (Device Management)
- Регистрация нового устройства (тип, модель, уникальный идентификатор)
- Привязка устройства к конкретному дому и комнате (или отвязка)
- Управление состоянием устройства: включить/выключить, выполнить команду, изменить режим
- Описание возможностей устройства (что оно умеет, например измерять температуру, включать свет, открывать ворота)

Домен телеметрии и мониторинга (Telemetry)
- Приём показаний от устройств (температура, освещённость, влажность и т.д.)
- Долговременное хранение и агрегация телеметрии для аналитики и отчётов
- Выявление аномалий (например, резкий скачок температуры, длительное отсутствие данных) и генерация событий

Домен автоматизации и сценариев (Automation)
- Создание и редактирование сценариев (например, "если температура в спальне < 20, включить обогреватель")
- Управление расписаниями (включение света по времени)
- Обработка событий (изменение состояния устройства, показания датчика, время по расписанию) и запуск соответствующих сценариев

Домен уведомлений (Notifications)
- управление каналами уведомлений (email, telegram, SMS)
- подписка пользователя на определённые типы событий
- отправка критических уведомлений (аварии, аномалии) по приоритетным каналам
- отправка информационных сообщений (например, "дверь открыта", "обнаружено движение")

Домен интеграции с устройствами (Device Integration)
- реализация поддержки протоколов (Wi-Fi, Zigbee, Matter, Modbus и др.) через единый интерфейс
- обнаружение новых устройств в сети
- управление обновлениями прошивок устройств (если поддерживается)

Домен интеграции с внешними сервисами (External Services)
- получение данных из внешних источников (например, прогноз погоды для оптимизации отопления).

### **4. Проблемы монолитного решения**

- Единая точка отказа
- Невозможность независимого масштабирования компонентов
- Сложность изменений и обслуживания
- Синхронные блокировки
- Сложно добавлять новые устройства
- Отсутствие кэширования данных внешнего API
- Нет механизмов повторных попыток при сбоях внешних сервисов

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия между микросервисами используется гибридный подход:
- Синхронные вызовы (REST / gRPC) – применяются для операций, требующих немедленного ответа, например:
  - Получение текущего состояния устройства (API Gateway → Device Management Service)
  - Проверка прав доступа (API Gateway → User Service)
  - Выполнение команды на устройстве (Automation Service → Device Management Service)
    Почему REST/gRPC: простота реализации, широкая поддержка, возможность использовать HTTP/2 для gRPC, что повышает производительность.

- Асинхронные события (Message Broker – Kafka / RabbitMQ) – для уведомления об изменениях и передачи потоковых данных:
  - Новые показания датчиков (Device Integration Service → Telemetry Service, Automation Service)
  - Изменение состояния устройства (Device Management Service → Notification Service, Automation Service)
  - События домов/комнат (Home Service → Notification Service)
    Почему асинхронность: обеспечивает слабую связанность, отказоустойчивость, возможность масштабирования подписчиков.

Внешнее API для клиентов (веб, мобильные приложения) реализовано через REST API за API Gateway, который маршрутизирует запросы к соответствующим микросервисам.

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {

		case "2":

	if sensorID == "" {

		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```
